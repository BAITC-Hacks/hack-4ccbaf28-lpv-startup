# LPV Match — план реализации

Статус этого коммита: зафиксированы архитектура, контракты данных и критерии проверки. Приложение ещё не реализовано. Не описывать запланированные возможности в README как готовые.

## Задача и пользовательский сценарий

Трек «Креативные индустрии», задача Firebird: подобрать до трёх подрядчиков для мероприятия из предоставленного организаторами каталога 66 анкет. Пользователь задаёт город, дату, категорию, формат мероприятия и бюджет; при необходимости — язык, продолжительность и пожелания к стилю.

Пример сценария: описать корпоратив обычным текстом → проверить распознанные поля → получить доступных подрядчиков с индивидуальными объяснениями → изменить дату и увидеть обновлённый результат.

Техническое задание: https://docs.google.com/document/d/1rhR2HFY164BrnkIP39N3usY9fNY4JeAgkPxEzbqL00w/edit

## Архитектура MVP

- Next.js и TypeScript: интерфейс и серверные API в одном локально запускаемом приложении.
- Локальный каталог из официального CSV; отдельная база данных и GPU не требуются.
- Код проверяет город, категорию, дату занятости, бюджет, формат, язык и длительность. Модель не может отменить эти ограничения.
- Ранжирование детерминированное: одинаковые входные поля дают одинаковый порядок, при равных баллах используется идентификатор анкеты.
- LLM разбирает свободный запрос и помогает объяснить найденных кандидатов. Объяснения опираются только на факты из анкет и расчётов.
- Поиск возвращает три различных состояния: найдено; категории нет в городе; категория есть, но кандидаты не проходят ограничения.
- Не выполняем бронирование, отправку заявок и уведомления подрядчикам.

## Экономия API

Модель для простого извлечения полей и модель для более сложных объяснений настраиваются отдельно: `OPENAI_MODEL_FAST` и `OPENAI_MODEL_REASONING`. Начальная конфигурация — `gpt-5.4-nano` и `gpt-5.4-mini`; доступность необходимо проверить на используемом аккаунте.

Фильтрация, проверка занятости и сортировка не расходуют токены. Планируются ограниченный контекст с тремя выбранными анкетами, ограничение длины ответов и кеш одинаковых запросов. Панель выполнения покажет использованную модель, задачу, фактические токены, время и оценочную стоимость. Без ключа должен работать явно обозначенный режим локального поиска с объяснениями по фактам.

Дообучение не требуется. Ключ хранится только в `.env.local`, обращения к провайдеру выполняются на сервере. NVIDIA подключаем лишь при реальной необходимости и подтверждённой совместимости API; наличие кредитов само по себе не требует второго провайдера.

## Этапы и проверяемые результаты

1. Импорт и проверка 66 анкет; реализация строгих фильтров и стабильного ранжирования; тесты граничных случаев.
2. Форма, карточки, причины отсутствия результатов и демонстрационные запросы.
3. Разбор естественного языка, объяснения и маршрутизация моделей; измерение расхода API.
4. Проверка сборки, три демонстрационных сценария, инструкция независимого запуска и финальная подготовка.

Пушим завершённые содержательные этапы несколько раз в час. Перед отправкой проверяем изменения коллеги; не используем force push и пустые коммиты. README ведёт коллега, технические заметки — в `docs/`.

## Критерии готовности

- В выдаче не более трёх анкет; занятый на выбранную дату подрядчик исключён.
- Бюджет и остальные заданные ограничения соблюдены; цена обозначена как начальная.
- Повтор одного запроса сохраняет порядок результатов.
- Для каждой карточки есть индивидуальные объяснения с проверяемыми основаниями.
- Различаются отсутствие категории и отсутствие подходящих исполнителей.
- При одном или двух результатах показано действительное количество и причина сокращения.
- Проверены массовая категория, редкая категория и пустая выдача.
- Ошибка API не ломает локальный подбор; режим без LLM честно обозначен.
- Секреты не попадают в Git, браузерный код и диагностические ответы.
- README соответствует фактически проверенной команде запуска и текущим возможностям.
